# Trusted host boundary and completed-cycle handoff

**Status: proposal only.** This document describes a candidate host integration for release review, merge approval, and publication. It is not an accepted operating procedure, and it does not enable a workflow, configure repository controls, provision credentials, select principals, or choose a storage service.

The CLI capabilities described here are implemented; the host that authenticates users, protects records, and serializes writes is not. See [release approval](release-approval.md), the [release policy](release-policy.md), and [publication reconciliation and execution](release-publication.md) for the component contracts.

## Implemented boundary

Issue #51 added strict approval-policy schema 2 to the existing read-only approval path. Its behavior is selected explicitly by a trusted policy; schema 1 remains supported with its existing behavior and no added review/check-readiness requests. Policy 1 records are not silently upgraded or treated as policy 2.

With schema 2, the verifier requires the configured allowed human's unambiguous latest submitted `APPROVED` review on the exact proposal head. For each configured workflow/event/job selector, it checks the latest invocation for the exact head and event, then its current attempt, unique successful job, check-run identity, expected App, and workflow check-suite identity. A newer failed or pending invocation cannot fall back to an older success. Readiness is checked again around capture/verification; changed identities fail closed. These are live API checks, not durable proof stored in the approval record.

`captureReleaseReview()` validates the exact open PR head, source, generated proposal, and current readiness, then returns a review record. `finalizeReleaseApproval()` binds that record to an explicit `merge` or `squash` attestation and reruns approval verification. Verification checks the actual human merger and landing SHA, expected parent structure, and exact reviewed tree. These APIs and their CLI commands are read-only. They do not authenticate who invoked them, establish that an input attestation came from a trusted action, persist output outside the caller's control, perform the merge, or publish artifacts.

The workflow ID and check identity do not pin or authenticate workflow source. Policy 2 does not set branch protection, ensure required checks are enforced at merge, authenticate the host caller, prevent policy changes by administrators, or provide an immutable audit trail. Existing policy/publication docs describe these as separate host controls.

## Proposed invocation and attestation flow

**Unapproved, unimplemented candidate (not an accepted choice):** One option for the host is two separate GitHub Actions `workflow_dispatch` invocations: one before merge for review capture and one after merge for finalization. Both would have to run trusted workflow code from the protected default-branch ref, rejecting dispatches that target another ref. No workflow currently implements this trigger or ref gate, and this document configures no repository protection. The host must never check out or execute the PR head, load policy from the PR, or treat PR text, artifacts, caches, or workflow inputs as authority. Use PR number and full head SHA as selectors only; compare both with live GitHub state before calling the CLI. The configured repository, release branch, approval policy, and tool version would come from independently protected host inputs.

1. **Capture before merge (candidate, unapproved).** A human authorized under a future owner-approved policy would invoke the trusted review-capture entry point. The host would derive the actor ID from the authenticated invocation context; it would not accept `approverUserId` as a caller assertion. It would reject non-human or unapproved actors, dispatch from the protected trusted ref, construct the target JSON with that actor ID, requested PR number, and exact head SHA, then call `capture-review --target FILE`. Policy 2, if explicitly selected, verifies the native review and required workflow evidence. The host would persist the returned record and invocation envelope before any merge step.
2. **Merge as the human (candidate, unapproved).** Under this proposal, the same future-authorized human would merge through GitHub's UI using an explicitly selected supported method. This is not an accepted merge path, and no merge-method or branch-protection setting is selected here. The host must not merge with its own `GITHUB_TOKEN` and claim the human was the merger: the verifier requires GitHub's actual `merged_by` identity to match the captured approver. Repository controls would have to restrict the allowed path independently.
3. **Finalize after merge (candidate, unapproved).** In this candidate flow, the same human would start a fresh trusted host invocation and explicitly attest `merge` or `squash`; there would be no default and no inference from commit parents. The host would derive the actor ID from that invocation, load the protected pre-merge record, and check that actor against the captured approver and GitHub's actual merger. It would obtain the landing SHA and PR identity from the repository API, construct the exact merge-attestation input itself, and call `finalize-approval --review FILE --attestation FILE`. The CLI independently checks the PR/head/landing, method-specific parents, exact tree, source freshness, policy/configuration identity, and current readiness. `rebase` is rejected.
4. **Publish only from finalized evidence.** A separately authorized host step uses the exact approved landing and independently protected publication policy and build receipt. It reruns the read-only inspector immediately before any approved write and uses the explicit publication executor only after a separate execution authorization. The host records the observed final state only after all configured tag, Release, asset, and image checks match. A matching tag or a successful CLI exit by itself is not cycle completion.

The proposed method field is an authenticated human attestation captured by the trusted host, not a claim that GitHub exposes a definitive merge-method field. The CLI validates the attested method against the resulting landing's structure and content. A mismatch stops finalization; the host must not rewrite the attestation to fit the observed commit.

For every invocation, bind the input/output record to the repository ID, PR number, exact head and source, actor ID, trusted workflow identity, run and attempt IDs, policy/configuration digests, and (after merge) landing SHA and explicit method. Use only values obtained from the authenticated host event, protected configuration, or bounded GitHub API responses. Never persist credentials or raw authorization headers. Do not treat an event payload, a record digest, or a workflow artifact as a signature.

## Trust boundaries and record protection

| Boundary                 | Trust requirement                                                                                                                                                                                                                                                   | Not provided by the CLI                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Human actor              | Authenticate the workflow invoker; derive their numeric account identity from the host event; require it to be in the independently approved principal policy and to match the actual reviewer and merger.                                                          | Authenticating the caller or approving any principal list.                                                        |
| PR and workflow evidence | Treat PR fields and API responses as untrusted data; use policy 2 when strict native review/check evidence is required; keep workflow source and called actions reviewed and immutable by revision.                                                                 | Pinning workflow source, enforcing required checks at merge, or proving which PR payload caused an Actions run.   |
| Policy and configuration | Load approval policy, release configuration, tool version, and publication policy from access-controlled sources outside the PR/proposal path. Changes require owner review and a fresh capture/verification.                                                       | Protecting policy files or selecting IDs, App identities, workflows, jobs, or allowed users.                      |
| Merge action             | Bind the pre-merge review to the same authenticated human, PR, and exact head; capture `merge`/`squash` explicitly; compare against GitHub's merged PR and the landing graph/tree.                                                                                  | Performing or authorizing a merge, or authenticating a supplied attestation file.                                 |
| Durable records          | Store records outside proposal-controlled refs and artifacts in append-only, create-only storage with immutability/retention controls. Separate record writers from principals that can alter policy or delete/shorten retention; audit exceptional administration. | Any storage, write-once semantics, retention, backup, or access control.                                          |
| Publication              | Give write credentials only to the single trusted publication path, scoped to the required repository/artifact destinations and lifetime. Recheck approval and publication state immediately before mutation.                                                       | Credential provisioning, credential exchange, host authorization, atomic publication, or a durable write journal. |

Use a protected record envelope around the existing CLI schemas rather than changing their fields. A useful envelope records a schema/version, record kind, repository and cycle identity, trusted workflow/run/attempt identity, authenticated actor, creation time, payload digest, and the exact payload bytes. Store review capture, merge attestation, finalized approval, publication inspection/receipt references, and completion as distinct immutable records. Use create-if-absent writes and append new attempt/outcome records; never replace a prior review, approval, or completion record in place. A digest detects accidental change but does not authenticate the writer or make mutable storage immutable.

The storage service, retention duration, key layout, backup/restore procedure, and break-glass administrators remain open decisions. Do not assume that Actions artifacts, branch files, caches, or ordinary versioning alone meet the immutability requirement.

## Serialized execution and recovery contract

Use one trusted writer path per repository and release branch. Serialize the critical section across finalization, publication writes, and completion recording; do not start a competing release cycle while a prior cycle is partial or has an unknown outcome. An Actions concurrency group can help prevent ordinary overlapping runs, but it is not an immutable ledger, a guaranteed FIFO queue, or by itself a durable lock/fencing mechanism.

The host needs a durable exclusion/ownership mechanism and a recovery rule for interrupted runs. No replacement writer may receive usable write authority until the prior writer is known to be stopped and its credential can no longer mutate GitHub. If the selected host cannot enforce that condition (including against a stale runner), it must not run publication writes. A lease or lock record by itself is insufficient if an expired holder can still use a live credential. Do not claim source-level atomicity: GitHub tag, Release, asset, and image operations are separate remote writes.

Append observable phase records rather than editing one mutable status object. A candidate lifecycle is `review-captured`, `merge-attested`, `approval-finalized`, `publication-in-progress`, then `complete`; failures and recovery attempts are separate records tied to the same exact cycle identity. A next cycle may start only after the host verifies the completed remote state and records that observation. An administrator's manual change is not an implicit completion or baseline advance.

On interruption, ambiguous response, lock loss, or partial write:

- Stop the current writer and establish that its credentials cannot continue to mutate state before recovery.
- Read the immutable record history and current GitHub/registry state. Run the read-only publication inspection; do not infer success from a timed-out request, local `performed` list, tag presence, or a previous green check.
- Investigate conflicts and unknown outcomes. Do not delete, move, overwrite, or blindly repeat remote writes. Use the existing explicit executor's documented fresh-inspect-and-retry behavior only after a human-authorized recovery decision and reacquiring exclusive ownership.
- Re-run approval verification at mutation time. A changed head, policy, configuration, required-review identity, selected workflow invocation, attempt, job, check, baseline, or landing is not repaired by replaying an old record. Capture/review again when the proposal is still open; otherwise stop for owner-directed recovery.
- Record the recovery decision and result as new immutable evidence. Do not advance the completed baseline or open a competing cycle until the configured publication is fully reconciled.

Policy 2's exact-head review and current workflow/job/App checks strengthen the input evidence, but do not replace caller authentication, record protection, or serialization. Policy 1 remains a supported compatibility mode; any decision to require policy 2 for newly enabled publication must be explicit and separately approved, not an implicit schema migration.

## Decisions and evidence required before enablement

This proposal intentionally does not decide or claim any of the following:

- Which human principals may invoke capture/finalization or approve policy changes; actual numeric IDs and review/merge separation rules need owner approval.
- Which workflow/App IDs, events, job names, policy version, branch protections, required checks, merge methods, or administrative controls are configured.
- Which host platform, immutable storage service, retention/backup policy, record namespace, lock implementation, or recovery authority will be used.
- How short-lived credentials are provisioned, what exact permissions they receive, who can grant them, and how revocation/expiry is proven before a replacement writer starts.
- Whether repository plan/visibility constraints support the intended protections and whether GitHub invocation actor identity behaves as required in the controlled workflow.
- Who approves publication execution, artifact/receipt production, and recovery from an irreversible or partially completed write.

Before enabling any live path, require an accepted host design; reviewed trusted workflow source and immutable action/tool references; approved principal and policy identities; independently protected policy, records, and credential boundary; verified merge-method and branch-protection settings; and controlled tests for actor mismatch, stale head, changed/latest review, newer failed run, rerun attempt changes, method mismatch, concurrent dispatch, runner interruption, and unknown publication outcomes. Confirm storage immutability and administrative recovery behavior. A documentation proposal, fixture test, or successful read-only verification is not that evidence.
