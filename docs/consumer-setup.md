# Set up Rolling Release

Use a GitHub repository whose release branch is `main`. Install a GitHub App with repository contents and pull request write access. Set `RELEASE_APP_ID`, `ROLLING_RELEASE_BOT` (the App login including `[bot]`) and the secret `RELEASE_APP_PRIVATE_KEY`. Allow the publication job to write the repository's GHCR package. Use repository rulesets to reserve writes to `release/next` and `release/changelog-backfill` for this App, including preventing human edits to the caller on the proposal branch. The read-only `pull_request` check loads workflow configuration from the proposal merge, so confirm this restriction before relying on it as a required check. Protect `main` for manual publication retries. Make the release workflow the sole writer of version and candidate image tags.

Copy [the release-cycle caller](../examples/release-cycle.yaml) to `.github/workflows/rolling-release.yaml`. It installs both the read-only proposal check and the release cycle. Install the separate manual backfill caller only when needed. The `consumer-v1` channel must be bootstrapped and verified before using the default ref; until then pin both provider references to a reviewed full commit SHA that contains these workflows. Keep both references on the same revision. Do not install the older separate release-quality example alongside this caller. For the first release without a stable tag, set `ROLLING_RELEASE_START_SHA` to the reviewed exclusive starting commit. The first releasable batch starts at 0.1.0. Returning consumers can adopt an existing stable tag.

Use conventional PR titles. A feature bumps minor, a fix, performance improvement or revert bumps patch, and a breaking title bumps major (minor before 1.0). Documentation and maintenance wait for the next releasable batch. An optional single `Required action: ...` line in a PR description appears in the changelog.

Set `RELEASE_LOG_WRITE_ENABLED=false` before installation, and manually dispatch the release cycle without a PR number to preview. Compare the proposed version, PR membership and changes with the reviewed release boundary before enabling writes. Configure the resulting `proposal-check / proposal` check as required for release proposals, coordinating the exact displayed name with branch protection. The caller requests read access for proposal checks and write permission ceilings for release events; the named App secret is forwarded only to the release workflow, which mints a scoped token only for eligible writes. To recover an interrupted publication, dispatch it from protected `main` with the merged release PR number in `retry-pr`; the retry verifies the original landing and existing matching tag, and refreshes the next proposal after publication. If the tag is missing, rerun the original promotion event. Update the provider channel to a revision supporting `retry-pr` before adopting the updated caller. After an ordinary PR lands the App refreshes one release PR. Review its changelog, version changes and captured metadata. Merging it authorizes a tag at the landing, a versioned Docker image and a GitHub Release with the reviewed notes. By default, configure your consumer Dockerfile at the repository root. To publish only a tag and GitHub Release, set `ROLLING_RELEASE_IMAGE_ENABLED=false` before generating the proposal. The proposal records the choice for review, and publication and retries follow that recorded choice even if the variable later changes. Rolling Release itself always requires its image. Inspect the source and digest reported by GHCR when recovering publication.

Run the separate manual changelog backfill to reconstruct historical sections from stable tags and available PR metadata. Review its changelog-only PR. If another PR merges into `main` first, rerun backfill before merging so the proposal includes the current tree. A missing or ambiguous association blocks the rebuild and identifies the affected release.

## Version files

| Project | Managed files                                                                                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| npm     | Root and shared `package.json` versions and first-party references, plus `package-lock.json` or `npm-shrinkwrap.json` mirrors                                                  |
| pnpm    | Shared packages selected by `pnpm-workspace.yaml` and their local importer entries in `pnpm-lock.yaml`                                                                         |
| Bun     | Shared package manifests and the text `bun.lock` format. Migrate older binary `bun.lockb` with Bun before adoption.                                                            |
| Python  | Static versions in `pyproject.toml`; local project entries in `uv.lock` or Poetry 2.1 lockfiles. Generated or backend-computed versions require a static version for adoption. |
| Rust    | Single crates and shared Cargo workspaces with inherited versions, local dependency requirements, and `Cargo.lock`                                                             |

In uv workspaces, members inherit dependency sources from the root and can override individual sources. The planner updates a pin when the effective source is unconditionally local. If a workspace source is conditional and the planner cannot establish that the pin is local in every case, it stops and names the dependency for review before rewriting the pin.

The writer expects participating packages to share the previous stable version. Ambiguous ownership or independently versioned packages require maintainer review. An image-only repository can release using the changelog and reviewed record alone.

The review record also retains the provider commit that generated it. Quality, promotion and publication select that producer from verified provider history for replay. If it is unavailable, restore access to the reviewed provider revision and rerun the original release event. Set `RELEASE_LOG_WRITE_ENABLED=false` to pause automatic writes while retaining manual preview.
